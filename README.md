# VPN Tray — 常驻分流代理 + 本地控制台

**[⬇ 下载最新版](https://github.com/ayuanjc/VPNTray/releases/latest)** · 解压即用，不用装 Python

Windows 托盘工具：内嵌 [mihomo](https://github.com/MetaCubeX/mihomo) 内核，一直挂着访问国外网站，
国内网站保持直连。节点切换走**本地网页控制台**（也可以从托盘菜单切）。
不需要管理员权限，不装驱动。

```
双击图标 / 右键「打开控制台」→ http://127.0.0.1:7892/
第一次用：先同意使用协议，再把订阅链接粘到「订阅」卡里，点「添加」
```

## 1. 它做了什么

| 环节 | 行为 |
|---|---|
| 订阅 | 首次运行在控制台填订阅链接；支持**多条订阅并存、一键切换**（按剩余流量排序）；之后启动自动拉取，默认每 6 小时更新并热重载 |
| 套餐 | 从订阅里解析「剩余流量 / 套餐到期」，左上角常驻显示，快用完/快到期变色 |
| 分流 | 内网直连 → 你的机场规则 → `GEOSITE,cn` / `GEOIP,CN` 直连 → 其余全部走代理 |
| 内核 | 托管 `bin/mihomo.exe`（v1.19.32），崩溃自动重启（退避，最多 6 次）；上次异常退出留下的孤儿内核会被自动清掉 |
| 系统代理 | 接管 Windows 系统代理到 `127.0.0.1:7891`，退出时精确还原你原来的设置 |
| 节点选择 | 每个节点先测延迟、**再用两次真实 HTTPS 请求验证**，只选中确实能上网的那个 |
| 健康看护 | 每 45 秒探一次当前节点，连续失败自动换（可关）；每 20 秒检查系统代理有没有被别的软件改走 |
| 测速 | 定时刷新全部节点延迟，控制台里直接看到 `38ms` / `超时` |

端口：混合代理 `7891`、内核 API `9091`、控制台 `7892`，全部只监听 `127.0.0.1`。
特意避开常见客户端用的 `7890 / 7897`，可以和别的代理软件共存。

## 3. IP 纯净度与排序

机场节点的「干净程度」直接决定 ChatGPT / 流媒体 / 银行风控能不能过。控制台可以逐个测：

| 入口 | 做什么 | 耗时 |
|---|---|---|
| 高级 →「纯净度·当前」 | 只测当前节点的出口 IP 画像 | 2 秒 |
| 高级 →「纯净度·全部」 | 逐个切过去重测所有节点，结束后自动回到原节点，**带进度条** | 2–4 分钟 |
| 高级 →「带宽测速」 | 对延迟最好的 10 个节点各下载 5MB 真实测速 | 1–2 分钟 / 约 50MB |
| 节点行里的延迟数字 | 只重测这一个节点，秒回 | <1 秒 |

检测过程中按钮会转圈并禁用，日志卡上方显示 `纯净度检测 37/74 · 50%` 的进度条。

**纯净度 0–100 怎么算的**

分两步：先拿到出口 IP 画像，再折算成分数。

1. **画像来源**：优先走 [One-IP](https://github.com/zhihui-hu/one-ip)（数据源 `ip.net.coffee`）。
   它给的是**综合信任分 + 判定标记**，比自己拿几个标志位扣分准得多。它挂了才回退
   `ipapi.is`，再不行回退 `ip-api.com`。当前用的哪一家会显示在分数后面，
   比如 `纯净度 62（One-IP）· 一般`。
2. **折算**：One-IP 给 `trust_score` 就直接当分数用，只在发现**落地国家 ≠ 节点标称**时
   再按本条扣分（这是 One-IP 看不到、但实际最影响使用的一点）。回退到 ipapi.is / ip-api
   时用下面的老算法。

从 One-IP 额外拿到了这些原本没有的信息，会显示在标签里：

| 字段 | 用途 |
|---|---|
| `trust_score` | 0–100 综合信任分，直接当纯净度 |
| `is_residential` / `company_type` | 判断住宅还是机房，比只看 `is_datacenter` 细 |
| `is_datacenter` / `is_vpn` / `is_proxy` / `is_tor` / `is_abuser` | 五类风险标记，命中就进标签 |
| `ai_verdict` | 该 IP 访问 AI 服务（ChatGPT/Claude 等）会被怎么对待 |
| `reddit_blocked` | 是否已被 Reddit 拉黑（风控严的站点会参考） |

回退到 ipapi.is / ip-api 时的老算法：

```
起评 100 分
  −45  Tor 出口          −40  被标记滥用        −30  机房 IP（AWS/阿里云等）
  −28  代理标记           −22  VPN 标记          −18  落地国家 ≠ 节点标称
  −15  爬虫库             −30  保留地址
```

| 分数 | 等级 | 含义 |
|---|---|---|
| 85–100 | 极洁净 | 住宅/ISP 原生 IP，ChatGPT、Netflix、银行都通 |
| 70–84 | 良好 | 能用，个别风控严格的站可能拦 |
| 50–69 | 一般 | 机房 IP，流媒体多半不行，ChatGPT 常被拦 |
| < 50 | 较差 | 被标记的脏 IP，建议别用 |

结果缓存在 `data/purity.json`，24 小时内不重复测。

**排序**：右上角下拉框可切换「按延迟 / 按纯净度 / 按带宽 / 按名称」，
地区分组也会跟着重排（纯净度排序时，最干净的地区排最前面）。
鼠标悬停节点能看到完整信息：等级、标签、出口 IP。

### 地区筛选与排序

- 列表上方一排 chip：全部 / 香港 / 日本 / 美国 / 台湾 / 新加坡 …，每个带节点数；
  点一下只剩这个地区，再点「全部」取消
- 搜索框按节点名、地区名、`IEPL`、`家宽` 等关键词过滤；**一旦输入就自动回到「全部」**，
  避免「选了日本又搜香港 = 一行都没有」
- 排序下拉：按延迟 / 按纯净度 / 按名称；纯净度排序时最干净的排最前面
- 筛选和排序都记在浏览器本地（`localStorage`），下次打开还是上次的样子
- 当前节点那一行高亮，点任意一行即切换
## 3.4 订阅管理

左上角标题旁边一直显示当前订阅的**剩余流量和到期时间**（从机场订阅里那两条
「剩余流量：xxx」「套餐到期：xxx」的假节点解析出来，不联网也能显示）。

左栏底部的「订阅」卡可以存**多条订阅链接**：

- 每条显示：备注名、剩余流量（`<20G` 转黄、`<5G` 转红）、剩余天数（`≤7` 天转黄）、
  节点数、是否使用中
- **按剩余流量从多到少自动排序**，正在用的那条置顶并高亮
- 点「切换」立刻切到那条订阅（重新拉配置、重建节点列表，当前节点选择会重置到最快可用）
- 点「删」移除；下面一行是「备注名 + 链接 + 添加」

订阅列表存在 `data/settings.json` 的 `subs`，当前用哪条记在 `sub_active`。
老版本的单个 `sub_url` 会在第一次启动时自动迁移成第一条订阅。

### 合并模式（同一机场的多个账号）

同一个机场经常给你好几个订阅链接（不同账号、不同套餐）。它们的**节点名是一模一样的**，
只是账号不同。点订阅卡标题右侧的「合并」按钮就进入合并模式：

```
顶上：合并 6 条 · 总剩余 569.0 GB · 6 条可用
       ↑ 所有账号的余额加在一起，一眼看到还能用多久

跑着跑着：
  订阅 3 余额 248 GB  → 用到 0.3 GB 以下
  ↓ 自动（不用你动手）
  订阅 1 余额 120 GB  → 接着跑，节点名不变
```

它做三件事：

1. **余额汇总**：每条订阅都读订阅响应头里的 `subscription-userinfo`（`upload/download/total/expire`），
   拿到的是机场后台真实的已用/总流量，比解析「剩余流量：xxx」这类假节点名准。
   启动后 18 秒刷一次，之后每 3 分钟刷一次。顶上显示的是**总和**。
2. **自动换号**：当前这条剩余 ≤ `0.3 GB`、或者已过期、或者链接失效读不到任何信息时，
   自动切到「还有余额、且余额最多」的那条。切之前记住你正在用的节点名，
   切完再选回去——因为同一机场节点名一致，所以**体感就是网晃了一下，节点没变**。
3. **不用管的失败**：所有订阅都耗尽时不会乱切，只在日志里记一笔。

关闭合并模式就回到原来的行为（只认当前这一条订阅）。
状态存在 `settings.json` 的 `sub_mode`（`merge` / `single`）。

## 3.5 AI 专项（Claude Code / Codex）

这栏解决三件事：**出口 IP 忽中忽外**、**时区对不上被风控**、**在同一账号上频繁换国家被盯上**。

先说对面到底在看什么（公开可查的检测面，不是猜的）：

| 检测面 | 具体做法 | 后果 |
|---|---|---|
| **时区一致性** | JS 上报 `Intl.DateTimeFormat().resolvedOptions().timeZone`，PHP 侧 `date_default_timezone_get()`；与声称地区比对 | 最强的单点判据。IP 在洛杉矶但时区写着 `Asia/Shanghai`，照样判中国 |
| **语言指纹** | `navigator.languages` 首位、`Accept-Language` 头 | 与 IP 地区不一致时计入风险分 |
| **出口 IP 类型** | IP 库里的 ASN 性质、`risk` 分、是否被滥用过 | 便宜的机房 IP 纯净度低，容易被 403 |
| **IP 跳变** | 同一账号短时间内在不同国家出口来回切 | 判「位置不可能 / 账号共享」，触发二次验证甚至封号 |
| **浏览器指纹** | UA、平台、时区、语言、WebGL 拼一起与 IP 地理比对 | 自动化脚本容易在这露馅 |
| **行为节奏** | 请求间隔、鼠标轨迹、输入速度 | API 调用管得松，网页端管得严 |

**本工具的对应动作：**

1. **AI 专用通道（独立代理组）**
   `claude.ai`、`api.anthropic.com`、`openai.com`、`api.openai.com`、`chatgpt.com`、`gemini.google.com`、
   `generativelanguage.googleapis.com`、`copilot.microsoft.com`、`grok.com`、`perplexity.ai`、
   `poe.com`、`huggingface.co`、`cursor.sh`、`openrouter.ai` 等 18 条域名规则单独走一个 select 组。
   **在你不手动切它之前，这个组的节点永远不变**——这是防 IP 跳变的核心。
   主组随便切、自动优选怎么跳，AI 流量纹丝不动。

2. **一键选最干净的节点**：下拉框按「纯净度 → 延迟」排序，直接标出 residential / 机房，
   点「切换」立刻生效并锁死在这个节点上。

3. **时区风险检测（重点）**：从节点名解析地区（`US/JP/KR/SG/TW/HK/MY/TH/VN/PH/DE/GB/NL/FR`）→ 对应时区，
   与本机时区比对，不一致就在卡片上挂警告：
   > ⚠ [节点] 落在 UTC+8 地区。时区/偏移是 Claude 最强的判据，换 US/JP/KR/EU 节点更稳。

4. **一键时区对齐**：把系统时区改成节点所在地（`SetDynamicTimeZoneInformation`），
   浏览器再上报就是 `America/Los_Angeles` 而不是 `Asia/Shanghai`。**改前自动存快照**，
   点「还原」原样恢复，不留痕。

5. **指纹自检**：报告出口 IP、国家、城市、ASN、是否机房、时区是否一致、浏览器语言，给 0–100 风险分。

6. **还原地区（快照）**：把检测前的原始出口地区存下来随时切回，避免「检测完忘了改回来」导致地区漂移。

7. **生成启动脚本**：一键产出 `.bat`——设好 `ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL` 走本地代理，
   并把 `TZ` 固定成节点时区再拉起 `claude` / `codex`，双击即用。

**用法（按重要性排）**

1. 开「AI 专用通道」，在下拉框里挑一个 **US / JP / SG** 且纯净度 ≥ 80 的节点，点「切换」
2. 看卡片警告——**出现时区警告就点「时区对齐」**，用完点「还原」
3. 平时**别频繁切 AI 组的节点**，一个节点用到底最安全
4. 第一次配环境点「生成启动脚本」，之后都从那个 bat 启动
5. 觉得哪里不对，点「指纹自检」看分数，> 70 就换节点或换时区

**说清楚局限**：这套只处理网络层和时区层的一致性。
浏览器 Canvas/WebGL 指纹、账号历史地域、支付方式、手机号归属这些，工具改不了，
也不该假装能改。

## 5. 三种上网姿势

| 场景 | 做法 |
|---|---|
| 平时（推荐） | 规则分流 + 系统代理开，国外走代理、国内直连，什么都不用管 |
| 只让浏览器走代理 | 关掉「系统代理」，浏览器扩展里填 `127.0.0.1:7891` |
| 某站想走代理 / 直连 | 换个节点试试，或把模式切「全局代理 / 全部直连」 |

## 6.1 火绒 / 360 / 电脑管家 拦住系统代理怎么办

有些安全软件（典型是**火绒**）会拦「未签名的程序修改 IE 代理设置」。被拦时的表现：

- `data/logs/app.log` 里反复出现
  `[WARNING] app: 系统代理被其它程序改动，重新接管回 127.0.0.1:7891`，
  紧跟着 `重新接管系统代理失败: [WinError 5] 拒绝访问。`（启动时那条是第一次接管失败）
- 控制台显示「系统代理」是关的，但 7891 端口明明在听
  （`curl -x http://127.0.0.1:7891 https://www.google.com` 能通），浏览器却还是直连
- 退出程序时可能留下 `ProxyEnable=1` 而没人监听 → **整台电脑上不了网**（见第 4 步）

这不是程序缺陷：在受保护的机器上，`VPNTray.exe`（未签名）写
`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 会被直接拒绝，
连它派生的 `reg.exe` 都被拒；而 `python.exe`、从命令行手动跑的 `reg.exe` 却能写。
也就是说防火墙跟着进程树走，只能靠放行解决。

### 第 1 步：把 VPNTray.exe 加进信任区（推荐，一次搞定）

1. 打开火绒主界面 → 右上角「**☰**」（或「设置」）→「**信任区**」
2. 点「**添加文件**」，选中 `VPNTray.exe`
3. 再把 `bin\mihomo.exe` 也加进去
4. 确定 → 托盘右键「退出程序」→ 重新双击 `VPNTray.exe`

### 第 2 步：还在拦，就去系统防护里放行规则

火绒 →「**安全设置**」→「**系统防护**」→「**系统加固**」（部分版本在「自定义防护」里）：

- 关掉 / 改成「允许」：「**注册表防护 → IE 设置 / 浏览器设置**」这一类
- 同理处理「**浏览器保护 → 主页与代理**」
- 弹出的拦截气泡里选「**允许**」并勾上「**记住本次操作**」，效果等同于第 1 步

### 第 3 步：确认真的放行了

重启程序后看 `data/logs/app.log`，应该出现：

```
[INFO] sysproxy: 系统代理已开启 -> 127.0.0.1:7891
```

并且不再有 `WinError 5`。命令行核对一下：

```powershell
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable
# 期望：ProxyEnable    REG_DWORD    0x1
```

### 第 4 步：已经断网了怎么救

退出时还原失败 = 注册表还指着已经关掉的端口。任选一种：

```powershell
# A. 命令行关掉系统代理
reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable /t REG_DWORD /d 0 /f
```

- B. Windows「设置 → 网络和 Internet → 代理」→ 关掉「使用代理服务器」
- C. 源码环境：`python -m vpntray.cli proxy off`
  （或者重新打开 VPN Tray 再走托盘「退出程序」，让它自己还原一次）

### 第 5 步：不想动安全软件的两条替代

- **只给浏览器走代理**：关掉控制台「系统代理」开关，浏览器装 SwitchyOmega 之类，
  代理填 `127.0.0.1:7891`（HTTP/SOCKS 混合口，不写注册表就不会被拦）
- **TUN 模式**：内核层接管流量，一个字节的注册表都不碰；需要右键「以管理员身份运行」，
  打开时程序会自动先关系统代理（见下面「TUN 模式」一节）

## 代理冲突清理

机器上同时开着 Clash Verge / v2rayN / SingBox 时，它们会抢同一套东西：系统代理注册表、
PAC 自动配置、TUN 虚拟网卡（直接改路由表）。表现就是「明明连上了却不通」或者「关掉代理还在走代理」。

「关于 · 帮助」卡里点 **检测**，会扫出：系统代理状态、其他代理进程、Up 状态的 TUN 网卡。
然后分三个按钮单独处理，**每一步都弹确认**，不会自动动手：

| 按钮 | 做什么 | 影响 |
| --- | --- | --- |
| 关闭系统代理 | ProxyEnable=0 并删掉 ProxyServer / PAC | 浏览器等立刻走直连 |
| 结束冲突进程 | taskkill 列出来的那几个 | 会关掉你别的代理软件 |
| 禁用 TUN 网卡 | Disable-NetAdapter | 需要管理员权限 |

自己的进程和 mihomo 内核永远排除在列表外。清理系统代理时会同时把「系统代理」开关记成关闭，
否则健康看护线程 20 秒后又会把代理装回去。

## 2.0：不再跳浏览器

以前双击托盘图标是往系统浏览器里塞一个标签页，用起来总像「开了个网页」。2.0 换成了原生窗口
（pywebview + WebView2，Win11 自带，不用另装运行时）：独立窗口、有任务栏图标、能记住上次的窗口大小，
关掉窗口进程就退干净，不会再留一个后台标签页。窗口和自己的后台是两个进程，靠本地 HTTP 通信，
所以界面和内核互不影响 —— 窗口崩了代理照跑。

关掉窗口只是关窗口，代理仍然在工作。要真正退出请用托盘右键「退出程序」或窗口里的「退出程序」。

## TUN 模式

「模式」卡里新增 TUN 开关。和系统代理的区别：

| | 系统代理 | TUN |
|---|---|---|
| 管到谁 | 读 WinINET 的程序（浏览器、大部分桌面软件） | 整台机器（游戏、命令行、不认代理的工具） |
| 需要权限 | 普通用户 | **管理员** |
| 原理 | 改注册表 + 广播设置变更 | 内核建一张虚拟网卡接管路由 |

两个不能同时开 —— 同时开会变成「流量进 TUN 又被系统代理指回 7891」的环。所以打开 TUN 时程序
会自动把系统代理关掉。开 TUN 需要以管理员身份运行，否则会直接告诉你原因而不是静默失败。

切换 TUN 会重启一次内核（约 2–4 秒），这期间网络会断一下。

## 实时连接

「连接」按钮打开一个实时列表：谁在联网、命中了哪条规则、走了哪个出口、各用了多少流量。
每 2 秒刷新一次，可以单独断开某条连接，也可以一键全部断开。

调试「某个软件连不上」时先看这里 —— 如果目标域名压根没出现在列表里，说明它没走代理（多半是不读系统代理的命令行工具）；
如果出现了但出口是 `DIRECT`，说明被规则放行了（这时候要去查规则，而不是换节点）。

## 2.0.1：修「点开控制台没反应」

2.0.0 有一个真实的坑：从浏览器下载的 zip 解压后，每个文件带一个「来自 Internet」标记
（`Zone.Identifier`）。.NET 拒绝加载带这个标记的程序集，于是 pythonnet 初始化失败、
窗口进程秒退。而当时的代码只判断「子进程有没有被创建」，所以既不回退浏览器、也不报错、
日志里一行都没有 —— 表现为点了完全没反应。

2.0.1 三处一起改：

1. **启动时自动清除标记**：主进程和窗口进程启动时都会扫一遍程序目录，把
   `Zone.Identifier` 删掉。不用去右键属性勾「解除锁定」。
2. **起窗口后验活**：`spawn()` 起完进程会等最多 6 秒，边等边检查窗口真的出现了没有；
   子进程秒退就返回失败。失败时先清一次标记重试，还不行就**自动回退浏览器**。
3. **失败必须说出来**：窗口进程现在也写日志（原来 `--window` 分支在 logger 初始化之前
   就 return 了）；真的起不来会弹一个说明框，托盘也会提示「原生窗口没起来，已改用浏览器打开」。

后台没启动、WebView2 缺失这类情况现在都有明确提示，不再静默。

已经装过 2.0.0 且正常，不升也行；如果点托盘没反应，覆盖升级到 2.0.1 即可。

## 2.0.2：修 codex / claude 连不上

用户的日志（`app.log` + `kernel.log`，17:34–18:01）暴露了两件事。

### 一、AI 走的是另一条线，主节点正常不代表 AI 正常

codex / claude 的请求走 `AI 稳定` 组，跟主节点不是同一条线。原来的健康检查**只测主节点**
（通过 7891 访问 `gstatic.com/generate_204`），AI 那条线挂了完全看不见 ——
用户看到的就是「别的都能上，就 codex 连不上」。

实测（同一时刻，只换 AI 节点，request 走同一个代理端口）：

| AI 节点 | `api.openai.com/v1/models` |
|---|---|
| 🇯🇵 日本原生-直连 | **HTTP 401**（通，只是没给 key）|
| 🇭🇰 香港-直连 | **HTTP 403**（通，Cloudflare 拦了下）|
| 🇰🇷 韩国家宽-中转 01 | **HTTP 401**（通）|
| 🇸🇬 新加坡-直连 | `SSLError`（TLS 被断）|
| 🇰🇷 韩国家宽-IEPL 01/02 | `SSLError` |

默认 AI 节点恰好是新加坡-直连，所以一开机 codex 就连不上。

2.0.2 加了 **AI 通道看护**：每 60 秒单独探测一次 `api.openai.com` / `api.anthropic.com`
（拿到任何 < 500 的响应就算通），连续 2 次不通就在 `AI 稳定` 组里换一个，
优先低延迟候选、每试一个都复测一遍。**不碰主节点**，换 AI 节点不会影响别的流量。

### 二、健康探测太急，一个抖动会被放大成三分钟断网

日志里的时间线：

```

17:42:17  健康探测失败（1）
17:42:59  健康探测失败（2）   → 判定节点挂了
17:43:01  开始重新选择
17:43:04  日本原生-直连 首次验证失败
17:43:07  选中 日本-中转 02
17:43:49  健康探测失败（1）   → 又挂
17:44:32  健康探测失败（2）   → 又重选
17:44:41/44/47  三个候选节点连续验证失败
17:44:58  选中 🇵🇭|菲律宾-IEPL 02
```

机场节点抖 30–60 秒很正常，但连续 2 次（约 80 秒）就换节点，换节点本身要断流几秒，
两次重选叠加就是三四分钟「整个软件像坏了一样」。改动：

- 容忍度 2 次 → **3 次**（约 120 秒）
- 单次探测超时 6s → **4s**（快速失败，别让界面卡住）
- 候选节点验证超时 6s → **3.5s**（8 个候选 × 6 秒 = 用户被断 8 次，比不切还糟）
- 探测失败现在会带上原因（超时 / 连接失败 / HTTP 状态码），日志里能直接看出是哪一环
- 节点恢复时补一行「节点恢复正常（之前连续失败 N 次）」

### 三、升级建议

如果你用 codex / claude 时断时续，直接升到 2.0.2。升级后不用管 AI 节点是哪台，
程序会自己挑一台能通的；也可以在「AI 专项」卡里手动指定。

## 2.0.3：修「自动更新之后软件就没了」

2.0.2 的日志停在最后一行：`18:32:49 更新器已启动，准备退出`，之后就再没有任何记录 ——
新版本没起来，旧版本也退掉了。用户面对的是一个打不开的软件。

排查下来是**两个独立的坑叠在一起**。

### 坑一：`tasklist` 在没有控制台的进程里会卡死

`update.cmd` 是用 `DETACHED_PROCESS` 起的（必须这样，主进程死了它才能继续跑）。
它原本靠这一行等旧进程退出：

```bat
tasklist /fi "IMAGENAME eq VPNTray.exe" | find /i "VPNTray.exe" >nul || goto gone
```

实测（同样的 flags、同样的重定向）：

- 纯 `for` + `ping` 循环 → 正常跑完，标记文件按时写出来
- 把 `tasklist` 那行加回去 → **一行输出都没有**，脚本原地卡住

`tasklist` 在无控制台环境里会阻塞在某个 console API 上。

**改法**：不再探进程，固定等 3 秒（主进程那边是 `os._exit(0)`，进程立刻消失），
文件万一还被占着就交给 `robocopy /R:10 /W:1` 自己重试。

顺带修了 `timeout /t 1` —— 它同样需要 stdin 手柄，在分离进程里也会失败。

### 坑二：`on_quit` 不保证进程真的退出

更新时调的是 `tray._quit`（只撤托盘图标），指望主消息泵自己收尾。
托盘窗口句柄丢了、或者 UI 线程卡在某个模态里，`PumpMessages` 就永远不返回，
进程挂着 → `update.cmd` 等不到 → 覆盖失败。

**改法**：更新前先 `app.shutdown()`（停内核、还原系统代理，这些必须做），
再撤托盘，然后 **`os._exit(0)` 硬退出**。更新本来就要进程死透，没什么好留恋的。

### 顺带加固

- 覆盖失败时**自动把旧版本拉起来**（原来只是 `pause`，用户看到的是一闪而过的黑窗口，然后软件没了）
- `robocopy` 输出写进 `%TEMP%\vpntray-update.log`（原来 `>nul`，出问题什么都看不到）
- 等待上限 40s → 60s，重试 `/R:3` → `/R:10`
- BAT 里的 echo 全改 ASCII（cmd 在 UTF-8 代码页下写中文会截断字，日志变乱码）

### 验证

用真实的 stage/launch 跑了一遍完整覆盖流程（旧目录里放 marker-old，payload 里放 marker-new）：


## 2.1.0：新图标 + 交互动效 + 界面重排

### 图标
之前任务栏和窗口左上角显示的是 **Python 的图标** —— `webview.start()` 没传 `icon`，
pywebview 就用默认图。现在显式传 `assets/app.ico`（`ui_native.py`）。

图标本身也重画了：深色圆角方 + 绿色渐变 V + 顶部微高光，出 16/32/48/64/128/256 六种尺寸。
四态分别是绿（运行）/ 灰（停用）/ 黄（忙碌）/ 红（异常），托盘和 exe 资源都用这一套。

### 动效
原则：只在「状态真的变了」的地方动，不做无意义的呼吸灯；全部走 `transform`/`opacity`，不触发重排。

| 位置 | 动效 |
|---|---|
| 卡片进场 | 轻微上浮 + 淡入（`riseIn`，0.36s） |
| 节点列表 | 逐行错开滑入（每行延迟 12ms，最多 24 行） |
| 当前节点行 | 一条缓慢扫过的绿光，告诉你「这是活的」 |
| 数字变化 | 上行/下行/累计/连接**真的变了**才闪一下（比字符串，不是每 1.5 秒无脑闪） |
| 开关 | 滑块回弹（`cubic-bezier(.34,1.56,.64,1)`），轨道颜色渐变，hover 有反馈 |
| 按钮 | 按下 `scale(.97)` 回弹 |
| 地图标记 | hover 放大 1.24 倍 |
| 横幅 | 从上方滑入 |
| Toast | 弹性从底部弹出 |

系统开了「减少动效」（`prefers-reduced-motion`）就全部关掉。

### 布局重排
原来「头重脚轻」的根源是左上角那个当前节点卡：四个**等大**的格子把「0 B/s」这种平时

## 2.2.0：任务栏图标真的换了 / 总开关 / 左右平衡

### 任务栏图标（这次是真修）

2.1.0 只做了 `webview.start(icon=...)`，但**任务栏按钮不认这个**。Windows 任务栏按
`AppUserModelID` 分组：进程没有显式 AppID 时按 **exe 路径**分组，于是 dev 下就是
`pythonw.exe` 的 Python 图标，窗口自己设的 `WM_SETICON` 完全管不到任务栏按钮。

三件事一起做才生效：

1. `SetCurrentProcessExplicitAppUserModelID("ayuanjc.VPNTray.Desktop")`，且必须在建窗口之前
2. 窗口 `shown` 之后再对 hwnd 补 `WM_SETICON`（大 32×32 + 小 16×16 各钉一次，重复 6 轮防被覆盖）
3. 打包时 exe 资源用同一套 ico

实测截图（`PrintWindow` 抓 `Shell_TrayWnd`）：任务栏最右侧那个深色圆角方 + 绿色 V 就是它。

### 总开关

界面最上方新增一个**代理总开关**（左栏第一张卡里那个 44px 高的大按钮）：

- 已连接 → 按钮显示「断开代理」（红字），点一下停内核 + 还原系统代理，**进程不退出**
- 未连接 → 按钮显示「连接」（绿底），点一下重新起内核 + 接管系统代理

后端 `POST /api/power {"on": bool}` → `App.power(on)`。和 `shutdown()` 的关键区别：
`power(False)` **不置 `self._stop`**，线程还活着，所以再点一次能立刻起来
（`shutdown()` 是给退出程序用的，一旦调过 `_stop` 就永久置位，之后起的线程会立刻退出）。

实测：点断开 → 按钮变「连接」、状态变「已断开」；点连接 → 按钮变「断开代理」、状态变「已连接」，0 JS 错误。

### 左右平衡

左栏原来堆了 5 张卡（当前节点 / 模式 / AI / 订阅 / 关于），右栏只有地图 + 列表，越往下越偏。

- 「关于 · 帮助」整块移出左栏，放到底部通栏（和免责声明一起）
- 当前节点卡改名「代理」，右上角显示实时状态（已连接 / 已断开 / 待添加订阅）
- 四个等大数字格子合成两行（上/下行大字、累计/连接小字）
- 「模式」卡 6 个开关行 padding 9→6，省 90px 高度
- 左栏 358 → 340，地图 `max-height` 收口

现在左栏 4 张卡、右栏 2 块，视觉上不再一边倒。

## 2.2.1：控制台窗口不再依赖 .NET + 安全软件拦截的系统代理

### 1. 控制台窗口：原生窗口起不来就换一个，不再掉进浏览器标签页

**病因**：在某些机器上（这台是装了「游戏加加 GamePP」的），`VPNTray.exe --window` 用 pywebview
（pythonnet + WinForms）建窗口时直接失败：

```
[ERROR] ui: 控制台窗口无法启动：RuntimeError: Failed to resolve
Python.Runtime.Loader.Initialize from ..._internal\pythonnet\runtime\Python.Runtime.dll
```

同一个 DLL 的字节完全一致（451584 字节，sha256 `2ebd4492e28442ef…`），换个路径有时又能加载，
有时在同一台机器上换个时间点就失败 —— GamePP 会往别的进程里注入，`clr.dll` 一起崩
（事件查看器 ID 1000，异常码 `0xc0000005`，出错模块 `GPP64.dll` / `clr.dll`）。
追了两个小时，结论是：**.NET 这条路在这类机器上不可靠，不该让控制台依赖它**。

**现在的打开顺序**（日志会写明用了哪条）：

| 顺序 | 方式 | 长什么样 |
|---|---|---|
| 1 | 原生 pywebview 窗口（`--window` 子进程） | 和以前一样的独立窗口，有 .NET 的机器上完全无感 |
| 2 | **Edge / Chrome 的 `--app` 模式窗口** | `msedge.exe --app=http://127.0.0.1:7892/ --window-size=…`，没有地址栏和标签页，看起来就是一个独立窗口 |
| 3 | 默认浏览器标签页 | 兜底，至少能用 |

- 浏览器按注册表 `App Paths` 找（`msedge.exe` / `chrome.exe`，HKCU + HKLM），找不到再试默认安装路径
- 先用「默认 profile」，不行再用一个专用 profile（`data/appwindow-profile`）
- 原生窗口失败会写 `data/window-mode.json`：`{"native_bad": true, "ver": "2.2.1", "why": "…"}`，
  下次开机直接走第 2 条；**版本号变了会重新试一次原生窗口**（升级后可能就好了）
- 子进程失败时只写日志、不再弹 MessageBox（以前会弹窗卡住父进程）

**判断成功的方式重写了**。原来按窗口标题前缀匹配 `VPN Tray 控制台`，但 Edge 的 `--app` 窗口在页面
加载完之前，标题就是 URL（`127.0.0.1_/`）—— 于是好好的窗口被判成失败，再开一个，最后放弃。
现在改成：`EnumWindows` 抓 `Chrome_WidgetWin_1` 类的可见顶层窗口，**前后句柄差集出现新窗口就算成功**，
标题只在之后 3 秒内补充到日志里。

### 2. 双击已在运行的程序也能弹出窗口

`run.pyw` 处理「第二个实例」时，原来直接调 `_focus_console()`（只认原生窗口），
原生窗口起不来时它就是空转。现在重写成：

```
ui_native.focus()（有原生窗口就激活它）
  → 没有就探 7892…7899 找到控制台端口
  → ui_native.open_console(port)（和托盘图标走同一条三级兜底）
```

顺带删掉了 `_spawn_console()` / `_focus_console()` 两个没人再用的函数。

### 3. 系统代理写入会重试，不再一次失败就整机没网

`sysproxy._write()` 对安全软件那种「瞬时拒绝」重试 4 次（0.12 / 0.24 / 0.36 / 0.48 秒退避），
日志记 `写注册表 %s 第 %d 次才成功…`。真的是权限被长期拦着（火绒内置防护就属于这种），
仍然把错误抛给上层 —— 此时按下文 [6.1](#61-火绒--360--电脑管家-拦住系统代理怎么办) 放行即可，
不要再重试到天荒地老。

### 4. 托盘提示文案更实

| 情况 | 提示 |
|---|---|
| 走 Edge/Chrome app 窗口 | 已用 Edge/Chrome 窗口打开控制台（原生窗口在本机起不来，详见日志） |
| 全都起不来 | 窗口都没起来，已改用浏览器标签页打开 |

### 升级提示

覆盖安装后 `data/` 保留，订阅和设置不用重填；因为版本号变了，会再问一次使用协议。
装过火绒的机器请先按 [6.1](#61-火绒--360--电脑管家-拦住系统代理怎么办) 放行，否则系统代理接管不上。

## 2.3.0：Steam / GitHub 各自一条专线

之前的配置里这两类没有独立出口：Steam 只有订阅自带的一个「蒸汽平台」组（很多机场根本没
有），GitHub 完全靠订阅规则漂，实测会被丢进「国际媒体」组 —— 那条线按 Netflix 的落地
点走，git clone 和游戏下载都慢到没法用，而且每次自动优选 / 自愈还可能换到另一个大洲的
落地，下载到一半断流。

这一版按「AI 稳定」的同一套结构给它们各建一个组，但目的相反：AI 要固定 IP，这两个要
**低延迟 + 不绕路**，IP 变了无所谓。

### 新增

| 组名 | 覆盖域名 | 默认偏好地区 |
|---|---|---|
| `Steam 加速` | steampowered / steamcommunity / steamstatic / steamcontent（下载 CDN）/ steamusercontent / steamgames / steamserver / steam-chat / steamconnecttest / steamdeck / s.team | 香港 → 台湾 → 日本 → 韩国 → 新加坡 |
| `GitHub 加速` | github.com（含 api / gist / codeload 的 git 传输）/ githubusercontent / githubassets / github.io（Pages）/ ghcr.io（镜像）/ github.dev / githubcopilot / github.blog | 香港 → 日本 → 新加坡 → 台湾 → 美国 |

- 面板新增「场景加速」卡片：两个开关 + 两个下拉，可以给每个场景单独钉一个节点，卡片上
  直接显示当前出口、延迟、域名条数，以及「是否和主代理是同一个节点」。
- 路由插在订阅规则**之前**（AI 规则之后），不会被订阅里的「国际媒体」抢走。
- 换机场 / 换订阅后节点名全变了时，启动和订阅更新都会校验钉选：名字不在组里就自动落到
  组头（偏好地区第一名），不会留下一个指向不存在节点的 `now`（那会让流量按 DIRECT 走，
  看起来就是「开了加速反而更慢」）。
- 和 AI 组一样遵守「建组与插规则必须同条件」：关掉开关或无可用节点时**组和规则一起不
  生成**，避免 mihomo 报 `group not found` 直接起不来。

### 配置项（`data/settings.json`，一般不用手改）

```json
{
  "steam_enabled": true,   "steam_node": "",
  "steam_prefer_regions":  ["香港", "台湾", "日本", "韩国", "新加坡"],
  "github_enabled": true,  "github_node": "",
  "github_prefer_regions": ["香港", "日本", "新加坡", "台湾", "美国"]
}
```

### 怎么用

打开面板 →「场景加速」→ 两个开关默认已开。想固定用某个节点就在下拉里选它，点「钉住」；
不钉就永远用组里第一个（偏好地区里排最前的那个）。Steam 下载慢时优先试「香港-直连 /
专线」类节点；git clone 慢时试「日本 / 新加坡」。

## 2.2.3：订阅能删掉了 / 延迟不再刷新一次就全空

这一版是拿另一台机器的真实日志（app.log 5525 行 + kernel.log 17 万行，10-19 → 10-31）查的，
两条都是**界面上看不出原因**的静默故障。

### 1. 删订阅：按钮点了永远失败，日志里一行都没有

前端从 1.8.0 起给删除传的是 `{"action": "del"}`，而后端 `set_sub_url` 只认 `"remove"`：

```python
# 旧代码：del 掉进 else，被当成「加一条空订阅」
elif action == "remove":
    ok, err = app.remove_subscription(...)
else:
    ok, err = app.set_subscription(url, name)   # url 为空 -> 报错
```

于是点「删」→ 后端走「添加订阅」分支 → 空链接被拒 →
界面弹「订阅链接必须以 http:// 或 https:// 开头」，列表一点没变；
因为请求压根没进删除流程，**日志里连一行记录都没有**（这也是为什么只能靠读代码找到它）。

现在后端 `remove` / `del` 都收，前端统一发 `remove`；剩最后一条时删除按钮直接置灰并
注明「至少留一个订阅」，空链接的报错也换成了人话「缺少订阅链接」。

### 2. 刷新延迟失败时，不再把已经测出来的延迟全部擦掉

`test_delays()` 原来在 `finally` 里无条件 `state["delays"] = delays`，
而 `ApiError`（内核没起来 / 机场整片超时 504 `all proxies timeout`）时
`delays` 是空字典 —— **一次失败就把面板上所有节点的延迟清成空白**，
看起来就像「刷新之后延迟显示不出来了」。

那份日志里这类失败有 118 次（90 次内核端口拒绝、28 次 504 全超时），
而且面板每 20 分钟自动测速一次，随时可能撞上。

现在：

- 测速**失败**：保留上一次的结果，只把原因记进 `state["delay_error"]`，
  节点列表头部会写「刷新延迟失败：…（显示 12 分钟前的结果）」，不再一片空白；
- 测速**成功**：整体替换，并写进 `data/delays.json`（含时间戳，12 小时内有效），
  **重启程序 / 刷新面板后直接读回来**，不用先手动点一次测速。

> 顺带说明：延迟是节点当下的状态，机场整体不通时内核本来就会整批超时。
> 面板现在保留旧数字并标注「X 分钟前」，是为了让人一眼分清
> 「延迟是旧的」和「面板坏了」。

## 2.2.2：日志不再被托盘图标刷屏 / 断流少了 / 版本号终于出现在日志里

这一版是拿别人机器的真实日志（12787 行、10-20 → 10-27）挖出来的，四条。

### 1. 托盘图标不再每 2 秒重读一次磁盘

托盘 tooltip 里带着实时上下行速度，**每 2 秒必然变化**，而旧代码把「tip 变了」当成
「图标也要重载」：每个 tick 都 LoadImage 一次 ico。图标正常时只是白费 IO；
**图标文件缺失时，每个 tick 打两条 warning**：

```
WARNING tray: 图标文件缺失，回落到运行中图标: D:\VPN\...\assets\app.ico
WARNING tray: 加载图标失败，使用系统默认图标: (2, 'LoadImage', '系统找不到指定的文件。')
```

那份日志里这两行各出现 **1289 次**，占全部 WARNING 的九成，真正的故障（节点整片不通）
被埋得几乎看不见。

现在 `_load_icon()` 按状态缓存 HICON，**只有状态（on/off/busy/error）真的变了才碰磁盘**；
文件缺失时每个候选路径只提示一次，一个 ico 都读不到就用系统图标并把话说一次：

```
WARNING tray: 图标文件缺失（打包时漏了 assets）：…\assets\app.ico（本条只提示一次）
WARNING tray: 没有任何图标文件可用，托盘改用系统默认图标（本条只提示一次）
```

实测同一路径连调 500 次：日志从 1000 行降到 2 行。

> 顺带说清一个容易误判的点：**这句「图标文件缺失」不是界面 bug，是那份包真的缺 assets。**
> 官方 zip 里图标在 `_internal/assets/app.ico`（已核对 v2.2.1 的 234 个条目），
> 别人二次打包时漏了 assets 才会出现。

### 2. 网络地址变化不再一抖就重建内核

热点 / 校园网会在两个地址之间来回横跳，旧逻辑一看到 `net_id()` 不同就 `restart_kernel()`，
**每次断流几秒**（那份日志里 46 次）。现在要求连续两轮采样都指向同一个新地址，且距上次
重建不足 2 分钟时先忍一轮；单纯跳变只记一行 info，不再断流。

### 3. 探测失败原因不再被覆盖

`_probe_detail()` 原来依次试 gstatic 和 cp.cloudflare，**只用最后一个 url 的原因覆盖 `last`**，
于是日志里永远只剩 `cp.cloudflare.com …`，gstatic 为什么挂没人知道。现在两个原因都留着：

```
健康探测失败（连续 3 次）：www.gstatic.com 连接失败（ConnectionResetError(10054,…)）| cp.cloudflare.com 超时 4s
```

节点验证失败也带原因了：`节点 HK-01 首次验证失败: …`，不再是光秃秃一句「首次验证失败」。

### 4. 启动第一行就是版本号

之前日志里没有任何版本行，出问题只能靠文案考古（那份 10-27 的日志就是靠
「缺少 WebView2 运行时」才反推成 2.0.1 代的 ui_native）。现在第一行固定是：

```
INFO app: VPNTray 2.2.2 启动（frozen=True，Python 3.12.10）
```

### 升级提示

覆盖安装后 `data/` 保留。如果日志里出现「图标文件缺失（打包时漏了 assets）」，说明手上
那份包不完整 —— 换回官方 zip（`VPNTray-<版本>-win64.zip`）即可。

## 2.5.8：机场订阅把 fake-ip 设成 28.0.0.1/8 —— 半个互联网当场消失

2026-11-13 现场（校园网 ZCST-CMCC）：网页能开但一切都很慢，DSH 的 AI 面板时通时断，
DNS-Client 事件 1014 刷屏（`dashscope.aliyuncs.com` / `registry.npmjs.org` / `raw.githubusercontent.com` 全中）。

翻到 mihomo 真正吃进去的配置才发现两行脏数据：

```yaml
dns:
  fake-ip-range: 28.0.0.1/8     # ← 28.0.0.0/8 是公网段（美国国防部）
  ipv6: true                    # ← 本机根本没有 IPv6 出口
```

**28/8 放在 fake-ip 里等于告诉 mihomo「整个 28 网段都是我的虚拟 IP」**：命中该段的真实目标会被
拉去 fake-ip，解析结果不可信；假 IP 还会跟真实公网地址撞车。而 `dns.ipv6: true` 让每次连接先等
一次 AAAA 超时。这两项都是**机场订阅下发的**，而 `configgen._dns()` 原来允许订阅直接覆盖。

2.5.8 加的护栏（订阅说什么都不好使，只认下面这两个池）：

| 项 | 规则 |
|---|---|
| `dns.fake-ip-range` | 必须是 IPv4、前缀 ≤ /16、且落在 `198.18.0.0/15` 或 `100.64.0.0/10` 里。不合规 → 丢弃订阅值，回退 `198.18.0.1/16`，日志记 WARNING |
| `dns.ipv6` | 订阅要开，但本机连不上 `2400:3200::1` / `240e:4c:4008::1` 的 53 端口 → 强制 `false` |

实测判定：

```
28.0.0.1/8     -> None（拒绝）
198.18.0.1/16  -> 保留
198.19.0.1/16  -> 保留
10.0.0.1/8     -> None
172.16.0.1/12  -> None
198.18.0.1/24  -> None（前缀太宽）
bogus          -> None
```

启动日志里现在能看到：

```
[WARNING] config: 订阅的 fake-ip-range=28.0.0.1/8 不是保留地址段，改用 198.18.0.1/16（否则整段公网会被当成虚拟 IP）
[WARNING] config: 订阅开启了 dns.ipv6，但本机没有 IPv6 出口，已关闭（否则每次连接先卡一次 AAAA 超时）
```

### 顺带查出来的三件事（不进代码，但遇到同类问题照做）

**1. 系统 DNS 别用运营商的。** 移动 `211.136.192.6` / `120.196.165.24` 在这条校园网链路上大量
超时（事件 1014，单次解析 448ms 起）。换掉：

```powershell
# 管理员
Set-DnsClientServerAddress -InterfaceAlias 'WLAN' -ServerAddresses 223.5.5.5,119.29.29.29

```

**2. 卸载过 TUN 模式，注册表里可能留着死 DNS。** 特征：`Get-PnpDevice -Class Net` 里有一个
永远「未连接」的 `Meta Tunnel [SWD\WINTUN\{GUID}]`，而
`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\{GUID}` 下还写着
`NameServer=198.18.0.2`。它不参与路由，但会被当成候选解析器 → 每次解析先超时一轮。清理：

```powershell
# 管理员
pnputil /remove-device "SWD\WINTUN\{03A3AABE-C890-F9C7-7DA2-DA7B6FF35C15}"
# 顺带清掉对应接口下的 NameServer 值
```

**3. 2.4G 挤爆时，先确认网卡是不是「住在 2.4G 不肯走」。** 这次一开始 `netsh wlan show interfaces` 显示
连在 2.4G ch6、接收速率 34 Mbps，而 `netsh wlan show networks mode=bssid` 头两遍扫出来同 SSID 的 4 个 AP
全在 2.4G（三个 ch6、一个 ch1）—— 看上去像是「这个网没有 5G」。**这是扫描不全造成的误判**：
把网卡高级属性里的 `首选频带` 设成 `3. 首选 5GHz 频带`、并重启网卡之后，它自己漫游到了
`84:32:ea:43:b4:56`（5G ch149，信号 91%）。差别是断崖式的：

| 指标 | 2.4G ch6 | 5G ch149 |
|---|---|---|
| 接收 / 发送速率 | 34 / 138 Mbps | **413 / 542 Mbps** |
| 网关 172.34.16.1 | avg 38–59ms，max 355ms | **avg 4ms（4–5ms）** |
| `223.5.5.5` | 12% 丢包，avg 214ms | **0% 丢包，avg 17ms（17–19ms）** |

管理员 PowerShell：

```powershell
Get-NetAdapterAdvancedProperty -Name 'WLAN' | Where-Object DisplayName -in '首选频带','吞吐量助推器','MIMO 节能模式'
Set-NetAdapterAdvancedProperty -Name 'WLAN' -DisplayName '首选频带'      -DisplayValue '3. 首选 5GHz 频带'
Set-NetAdapterAdvancedProperty -Name 'WLAN' -DisplayName '吞吐量助推器'  -DisplayValue '已启用'

```

## 2.5.7：AI 面板报 cannot resolve —— 本地 53 端口根本没人服务

2026-11-13 现场：网页、ChatGPT 面板、git 全都正常，只有 DSH 的 AI 请求一片红：

```
重试延迟：459毫秒
失败原因：502 "cannot resolve tunnel destination dashscope.aliyuncs.com (ETIMEDOUT):
local name resolution failed and a fresh resolver thread also failed — the local resolver
may be unreachable or taken over by another DNS service (VPN/MagicDNS)"
```

**排查过程**（结论是一行，但要证明它）：

```powershell
node -e "console.log(require('dns').getServers())"      # → [ '127.0.0.1' ]
node -e "require('dns').resolve4('dashscope.aliyuncs.com',(e,a)=>console.log(e&&e.code,a))"
# → ECONNREFUSED（1 毫秒）
node -e "require('dns').lookup('dashscope.aliyuncs.com',(e,a)=>console.log(e&&e.code,a))"
# → ok，8.152.159.24 / 39.96.213.166
netstat -ano | findstr ":53 "                            # → 一片空白，没人监听
nslookup dashscope.aliyuncs.com 127.0.0.1                # → No response from server
nslookup dashscope.aliyuncs.com 211.136.192.6            # → 正常
```

同一个域名，`lookup` 能解析、`resolve4` 不能，这是**两条完全不同的解析通道**：

| 通道 | 走谁 | 谁来解析 | 这台机器上的结果 |
| --- | --- | --- | --- |
| `dns.lookup()` | 系统 getaddrinfo | Windows Dnscache 服务 | 正常 |
| `dns.resolve4()` | Node 内置 c-ares | **直接问 `dns.getServers()`** | 全部失败 |

而 Node 拿到的服务器列表是 `127.0.0.1`，机器上却没有任何进程在 53 上应答。浏览器、curl、
PowerShell 都走 Dnscache 所以看不出问题；**凡是自带解析器的程序（Node/c-ares、Go 的 netgo、
部分 Rust CLI）一律 ECONNREFUSED，表现就是“网页能开、AI 面板全挂”**。

顺带排掉了两个常见误判：网络没坏（`curl --noproxy '*' https://dashscope.aliyuncs.com/` → 404，
2.27 秒；走 7891 → 404，0.33 秒）；mihomo 也没抢 53（配置里 `tun.enable: false`，`dns` 段没有
`listen`，`netstat` 也证明 53 空着）。真正剩下来的是**一条早就被删掉的本地解析器留下的残影**
——注册表里接口 `{03a3aabe-…}` 还挂着 mihomo TUN 时代的静态 DNS `198.18.0.2`，Node 把
`127.0.0.1` 和这个地址当成上游，挨个试，挨个超时。

**修法：VPNTray 自己补上这个洞**（`vpntray/dnsguard.py`）

- 在 `127.0.0.1:53` 起一个极小的 UDP + TCP 转发，上游 `223.5.5.5 / 119.29.29.29 / 114.114.114.114`，
  带缓存（TTL 夹在 5–600 秒，最多 2000 条）、单查询 2 秒超时、最多 32 个并发。
- **只在没人占 53 时启动**：bind 失败就安静退出，面板上写「端口被占用（…），已有本地解析器」。
  所以装了 AdGuard、SmartDNS、mihomo 的 DNS 监听，或者用 TUN 模式的用户，不会被抢端口。
- 只监听 `127.0.0.1`，不对外网开放，不当网关，不改任何系统设置。
- **启动后每 20 秒自检一次**：端口还在自己手里吗？还能答出来吗？连查三次不通就重启守护线程。
  托盘一跑就是几天，中间被别家软件抢了端口又放开、自己的收包线程意外退出，都能自己爬回来。
- 面板新增「本机解析」卡片：显示是否在服务、为什么没起来，一个「测一次解析」按钮（真的往 53 发
  一条 A 查询，返回毫秒和记录数），一个开关（`dns_guard`，默认开）。

**手工兜底（不想装新版，或者想从根上治）**

改成真实 DNS 服务器，管理员 PowerShell 一次：

```powershell
netsh interface ip set dns name="WLAN" static 223.5.5.5 primary
netsh interface ip add dns name="WLAN" 119.29.29.29 index=2
ipconfig /flushdns
node -e "console.log(require('dns').getServers())"   # 应该不再是 127.0.0.1
```

如果 `getServers()` 还是 `127.0.0.1`，说明是**全局**覆盖
（`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\NameServer`）或某个代理软件在启动时
写回来的 —— 前者删掉那个值即可，后者请把它的“系统 DNS”关掉。

## 2.5.6：点了没反应 —— WMI 卡死时进程永久阻塞（真凶是 setuptools 钩子）

2026-11-08 现场：梯子用着用着没了，双击图标毫无反应。任务管理器里躺着 **4 个 VPNTray.exe，CPU 都是 0，没有窗口、没有托盘、没有端口**，`app.log` 一行没写，事件日志也没有崩溃记录。

py-spy 抓栈定案（4 个进程一模一样）：

```
_wmi_query (platform.py:327)
_win32_ver (platform.py:388)
win32_ver (platform.py:450)
uname (platform.py:922) → system (platform.py:987)
robust_remover (_distutils_hack/__init__.py:207)
<module> (_distutils_hack/__init__.py:230)
... distutils → pkg_resources → setuptools
pyi_rth_setuptools (PyInstaller 运行时钩子)
```

链条：PyInstaller 只要打进 setuptools，就会注入 `pyi_rth_setuptools` 运行时钩子，它在**任何应用代码之前**执行；`_distutils_hack.do_override()` 导入 distutils → pkg_resources → `platform.system()` → Windows 的 `_wmi_query`。本机 WMI 服务（winmgmt）已经卡死，这一句查询永不返回 —— 进程就死在那儿。它死得比 `paths.ensure_dirs()` 还早，所以连 boot.log 都留不下来。

同一台机器上 `platform.system()` 直接卡住（`timeout 12 python -c "import platform;print(platform.system())"` → rc=124），PyInstaller 自己也构建不动，最后靠 `sitecustomize` 把 `platform._wmi_query` 换成抛 OSError 才把包打出来。

修法：

| 改动 | 位置 | 作用 |
| --- | --- | --- |
| 打包排除 `setuptools` / `pkg_resources` / `_distutils_hack` | `release.ps1`、`build.ps1` | 钩子不再注入，启动路径没有 WMI 依赖 |
| 反馈面板不再用 `platform.system()` | `vpntray/feedback.py` `_os_info()` | 改读注册表 `CurrentVersion`，卡死的机器上也能立刻返回 |
| 启动时兜底 `SETUPTOOLS_USE_DISTUTILS=stdlib` | `run.pyw` 顶部 | 源码运行/开发机保险（frozen 钩子更早，真正靠的是上面那条） |

验证（同一台 WMI 卡死的机器）：

- 2.5.5 的 exe 里有 `pyi_rth_setuptools`（998 字节）；2.5.6 的 PKG 里没有（`pyi-archive_viewer -l` 对比）
- 2.5.6 不设任何环境变量冷启动 → `boot.log` 正常写满，7892/7891/9091 三个端口全起
- 面板 `/api/state` → `ver=2.5.6`；google 204 / baidu 200

顺带修的两处（这次现场暴露的）：

- 开始菜单里躺着两个指向 **旧版 `E:\VPNTray-2.5.1`** 的快捷方式，双击就是那个卡死的老版本 —— 已清掉重复项并改指当前安装。
- 系统代理开关还指着 `127.0.0.1:7891`，而进程已死 = 全网黑洞。判断实例身份要看 pid，别只看端口。

## 2.5.1：校园网 / 内网不再被代理吃掉

清一次本机网络时挖出来的两个真问题，都是「地址段看着像公网，其实是你家内网」：

- **系统代理例外少了两个段**。`sysproxy.BYPASS` 只放了 RFC1918（`172.16–172.31`），
  可本校校园网用的是 `172.50.86.0/24`（客户端）和 `172.32.0.0/16`（Dr.COM 认证门户
  `172.32.253.17`）—— 这两段在 RFC1918 之外。结果浏览器访问门户、校内站点、NAS 时会被
  丢进代理，认证页打不开或者被绕到境外节点。现在 BYPASS 补上 `172.32.*`、`172.50.*`、
  `169.254.*`，并且每 20 秒的健康看护重写例外时会一并带上，不会被覆盖回去。
- **分流规则同理**。`configgen.LAN_RULES` 加了
  `IP-CIDR,172.32.0.0/16,DIRECT,no-resolve` 和 `IP-CIDR,172.50.0.0/16,DIRECT,no-resolve`，
  不再靠 `GEOIP,CN` 兜底 —— 校园网这几段随时可能被判成境外，一判错内网服务就全断。

配套的本机加固（一次性，脚本在 `_uiprobe/harden.ps1`）：

| 动作 | 说明 |
|---|---|
| `Set-NetFirewallProfile -Profile Private -Enabled True` | 专用网络防火墙原本是**关的**，一旦网络类别从「公用」翻成「专用」就整层失效 |
| 禁用 20 条「文件和打印机共享」入站规则 | 校园 Wi-Fi 是 `Open / Cipher: None`（无 L2 加密），445 不该对同网段开着 |
| 删 `netsh portproxy 7897 → 7891` | 旧代理工具残留，监听者是 iphlpsvc |

## 2.5.0：GitHub 不再靠运气（自动组 + 自检 + git 代理对齐）

2.3.0 给 GitHub 建了专线，但它只解决「规则被别人抢走」。真正把 GitHub 弄死的是另外三件事，
这一版逐个按死：

| 现场症状 | 真实原因 | 2.5.0 的做法 |
|---|---|---|
| 网页能开、`git clone` 报 `unexpected eof while reading` | `GitHub 加速` 组钉在一个已经死掉的节点上，网页靠重试勉强打开，git 一次 TLS 就断 | 新增 `GitHub 自动` fallback 组（只装**测速通过**的节点），专线默认走它；钉住的节点测不通时自动退回自动组 |
| 浏览器能开、Release 资产与 `ghcr.io` 打不开 | 规则只按域名后缀匹配，`github-production-release-asset-*.s3.amazonaws.com` 这类老直链走的是别的域名 | 补 `DOMAIN-KEYWORD,github-production-release-asset` + `DOMAIN,github-cloud.s3.amazonaws.com` |
| 换过 Clash / 别的客户端之后 git 全挂 | `git config --global http.proxy` 还指着 `127.0.0.1:7897`（那个端口现在被 svchost / WSL 转发占着，连上立刻 EOF） | 启动时对齐 git 全局代理到当前混合端口；只改「指向本机」的值，指向公司网关的外部件一律不碰 |
| 「到底哪一环坏了」说不清 | 只有一个总开关，没有分层诊断 | 面板新增「GitHub 自检」：网页 / API / raw / Release 资产 / 容器镜像五项 + 真跑一次 `git ls-remote` |

### 1. `GitHub 自动`：只从活节点里挑

`GitHub 加速` 变成两层：外层还是 Selector（能钉节点），第一位是新的 fallback 组
`GitHub 自动`。

```yaml
- name: GitHub 自动
  type: fallback
  url: https://github.com/robots.txt
  interval: 180          # 每 3 分钟自己复查一次
  timeout: 3000
  lazy: false
  proxies: [ 🇯🇵|日本原生-中转 01, 🇹🇼|台湾-中转 01, ... ]   # 只放测速通过的，按延迟升序
- name: GitHub 加速
  type: select
  proxies: [ GitHub 自动, 🇭🇰|香港-IEPL 01, ... ]
```

- 成员来自上次测速结果（`data/delays.json`），**没测通的节点不进自动组** —— 这就是
  「100 个节点只有 12 个活」时 GitHub 还能用的原因。
- 一个活节点都没有时退回旧行为（全量成员），不至于因为「没测速数据」把专线弄没。
- 启动时如果发现 `github_node` 钉着的节点已经不在测速结果里，直接改钉自动组并存盘，
  不再死抱着那个挂掉的香港-IEPL 01。
- 关掉「自动组」（`scene_auto: false`）就回到单层 Selector，行为和 2.4.0 完全一样。

### 2. 面板上的 GitHub 自检

「场景加速」下面多了一行 GitHub 体检框：

- 五个探针：`github.com`（网页）、`api.github.com`、`raw.githubusercontent.com`、
  `objects.githubusercontent.com`（Release 资产）、`ghcr.io/v2/`（容器镜像）。
  判定标准是「TLS + HTTP 全程通了就算通」，所以 ghcr 返回 401、资产返回 404 **都算正常**
  —— 只有超时、连接被重置、SSL EOF、5xx 才算坏。
- 一段 `git ls-remote --heads https://github.com/git/git` 的真实结果（拿到几个 ref、耗时多少）。
  浏览器能开不等于 git 能拉，这两个必须分开看。
- 点「GitHub 自检」：发现某项不通，就用 GitHub 自己的地址给自动组重测一遍，把出口拉回
  健康节点，然后**再测一次**给你看结果。
- 点「对齐 git 代理」：立刻执行一次代理对齐（平时启动时已经自动做过）。

```json
// POST /api/github/check   → { ok, github: { ok, bad: [], git: {ok,refs,ms}, node, note, items[] } }
// POST /api/git/proxy      → { ok, note, value }
```

### 3. git 代理对齐的边界

只改这两种值：`http://127.0.0.1:<port>`、`http://localhost:<port>`、`http://[::1]:<port>`
（含不带 scheme 的写法）。`socks5://...`、公司网关、PAC 一律不动，只在日志里写一句
「指向外部代理，不自动改」。改写成功时面板会显示 `http.proxy http://127.0.0.1:7897 → 7891`。

### 4. 配置项

```json
{
  "github_enabled": true,
  "scene_auto": true,        // 建「GitHub 自动」fallback 组（默认开）
  "github_heal": true,       // 自检发现不通时自动换节点（默认开）
  "git_proxy_sync": true     // 启动时对齐 git 全局代理（默认开）
}
```

### 5. 实测（本机，2026-11-06）

同一条订阅、同一时刻，对着出问题的 2.2.x 实例和 2.5.0 的配置各测一遍：

| 项 | 2.2.x（组钉死在死节点） | 2.5.0（自动组） |
|---|---|---|
| `github.com` | 200 / 2510ms | 200 / 1307ms |
| `api.github.com` | 200 / 1542ms | 200 / 1330ms |
| `raw.githubusercontent.com` | 200 / 4892ms | 200 / 1048ms |
| `objects.githubusercontent.com` | **SSL EOF** | 404（通） |
| `ghcr.io/v2/` | **SSL EOF** | 401（通） |
| `git ls-remote` | **失败** `TLS connect error: unexpected eof` | 8 refs / 2041ms |

另外把 `GitHub 加速` 人为钉到 `🇭🇰|香港-IEPL 01`（已死），点一次自检：
五项全断 → 组内重测选中 `🇯🇵|日本原生-直连`（141ms）→ 复测五项全绿、`git ls-remote` 8 refs。

> 机场本身的问题这一版治不了：那天 100 个节点只有 12 个活。自动组能保证「活着的那个在
> 干活」，但活节点数为 0 时它也只能告诉你「机场中转段整片失效」。

## 2.5.3：把底座修硬（9 个阻塞级缺陷 + 13 处隐患）

这一版没有新功能，全是「早晚出事但平时看不出来」的地方。逐项都做了改造前后等价验证。

### 会真的把梯子搞死的（阻塞级）

| 位置 | 症状 | 现在 |
| --- | --- | --- |
| `kernel.start()` 全程持锁 | 内核卡在就绪等待时，退出/重启被拖 20 秒以上，托盘像死了一样 | 锁只护进程句柄；端口探测与就绪等待在锁外，`stop()` 实测 0ms 返回 |
| 看门狗一次重启失败就放弃 | 端口一时被占 → 自动重启直接放弃 → 内核死、系统代理还指着死端口 = 全网黑洞 | 重试到 6 次，退避 2/4/8/16/30 秒，成功即恢复；每次失败都写日志 |
| `kernel.log` 不轮转 | 实测涨到 24.3MB / 95101 行，99.4% 是同一条失败连接 | 超过 8MB 启动前滚成 `kernel.log.1` |
| 面板后台线程异常全静默 | `pythonw` 下 stderr 是 None，点了没反应，日志里一个字都没有 | `_bg` 统一兜住异常并写明任务名 |
| GitHub 自检同步跑 37.7 秒 | 面板 HTTP 线程被按住，前端转圈、浏览器先超时 | 改成后台线程，接口立刻返回，前端轮询 `gh_busy` 收尾 |

### 平时不响、出事很难查的（建议级）

- `requests.Session` 跨线程共用 → 每个线程一份（面板 / 七个后台循环 / 自检线程都在调同一个客户端）。
- `settings.json` 默认值补上 `sub_mode` / `sub_hash` / `probe_on_select` / `agreed_version`，不再靠 `.get` 隐式兜。
- 7 处裸 `int(settings["mixed_port"])` → 统一走 `_int` 收边界（脏值不再直接抛 ValueError）。
- `_port` 在 kernel / configgen 逐字节重复 → 合并到 `settings.port_setting`。
- 端口被占时不再「名字查不到就盲杀」，只对 mihomo 下手。
- 订阅下载边读边卡 8MB 上限（以前整包进内存之后才检查，一个 800MB 的订阅能先把机器拖死）。
- 纯检/测速结束还原原节点失败会写日志（以前 `except ApiError: pass`）。
- `shutdown()` 幂等：重复调用不再重放「还原系统代理 / 停内核」。
- 纯净度检测的 `except BaseException` 收窄成 `Exception`（别吞 KeyboardInterrupt / SystemExit）。
- 更新按钮连点不再下两份包（判断与置位进同一把锁）。
- `state` 补 `conflict` / `sysproxy_hold` / `gh_busy` 初值，前端不用再猜键在不在。
- 面板路由表只建一次（以前每个 POST 重建 41 条闭包）。
- 仓库内新增 `tests/`：10 条不联网、不起内核的用例，`python -m pytest tests -q` 两秒跑完（以前所有验证脚本都在仓库外）。

### 怎么验的

- 内核：临时目录造假日志验证轮转；`stop()` 计时；看门狗连续失败 2 次后仍能恢复；试满 6 次才放弃；非 mihomo 占用不杀 —— 8 条全过。
- 配置：11 个场景（真实订阅缓存 / 无测速数据 / AI 关 / 场景全关 / 坏端口 / TUN 开 / mini …）与改造前逐字节比对 YAML，0 差异。
- 面板：41 条路由与改造前逐条比对响应与调用序列，0 差异；`/api/github/check` 现在 0ms 返回（原来 37.7 秒）。
- GitHub 特化：300 个场景比对 6 个方法的返回值/调用序列，0 差异；真网自检五项 + git 实测照旧。
## 2.5.2：修「双击没反应」——同步模态框 + 僵死互斥体

### 现场（2026-11-07 16:37）

托盘程序与 mihomo 内核在同一秒一起消失，`app.log` 和 `kernel.log` 都停在 16:37:3x，
没有 shutdown 日志、没有 CrashDumps、事件日志里也没有 Application Error。
之后 16:51–16:53 连着起了 8 个 `VPNTray.exe`：每个 CPU 0.15 秒、内存 32MB、
没有窗口、**没有监听任何端口**、`app.log` 一行没写。而此时系统代理还指着 127.0.0.1:7891 ——
对外表现就是「整个网都断了」。

用 py-spy 附加到这些进程，栈是这样的：

```
_msgbox (run.pyw:53)
main (run.pyw:116)
<module> (run.pyw:211)
```

### 两条根因

1. **`_msgbox` 是同步 `MessageBoxW`**。启动时发现命名互斥体 `Local\VPNTray_SingleInstance_9f3a`
   已存在 → 打开已有控制台失败 → 弹框 → 没人点，进程就永远停在那一行。
   用户以为没启动，再点一次，于是又堆一个 —— 8 个僵尸进程全是这么来的。
   它们既不启动服务，也不释放互斥体，还占着位置。
2. **判断「已经在运行」只看互斥体，不看服务**。互斥体是上次异常退出留下的空壳时，
   程序依然认定「另一个实例在跑」，于是每次都走「打开别人的控制台 → 失败 → 弹框」这条死路。

顺带查出一个藏了三个版本的 bug：`_open_existing()` 认控制台的方式是读首页前 2KB 找
`"VPN Tray 控制台"`，而页面标题其实叫 `VPNTray` —— 永远匹配不上。也就是说，
从 2.0 起「再点一次 exe 想打开控制台」就没成功过，一直是靠弹框搪塞。

### 2.5.2 的改法

| 位置 | 改动 |
| --- | --- |
| `run.pyw` `_msgbox()` | 改非阻塞：后台线程弹框，最多等 12 秒，进程该退就退。启动/退出路径不再被模态框钉死 |
| `run.pyw` `_second_instance()` | 判据换成「有没有活的服务」：面板端口应答 → 转发打开；只有内核端口在 → 提示等几秒；**两个都不在 = 空壳互斥体，直接接管启动** |
| `run.pyw` `_probe_console()` | 改成请求 `/api/state` 认 `ver` 字段，不再依赖页面文案 |
| `run.pyw` `_open_existing()` | `ui_native.focus()` 放进线程并设 5 秒预算（对方进程卡死时它会一起挂住），整体 ≤ 8 秒 |
| `run.pyw` `_boot()` | 新增启动路标 `data/logs/boot.log`：logger 起来之前每一步写一行（start → mutex → paths+logger → unblock → App → 托盘 → WebUI → 消息循环），超过 256KB 自动截断 |
| `ui_native.py` `unblock_tree()` | 剪枝：跳过 `data/`、`bin/`、`build/`、`release/` 与 >8MB 的文件，不再每次启动都全目录扫一遍 |
| `autostart.py` `refresh()` | 自启项里写的还是旧目录那个 exe 时，启动即改写成本进程路径 —— 免得新版解压到新目录、开机跑的还是旧版本 |

以后再出现「双击没反应」，先看 `data/logs/boot.log` 最后一行停在哪个阶段，
不用再装 py-spy 附加进程。群里让人发一份 boot.log 就够了。

### 升级提示

覆盖安装保留 `data/`。互斥体空壳现在会被自动接管，不需要重启电脑、也不用手动结束进程。

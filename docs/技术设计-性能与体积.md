# 技术设计：性能与体积（1.x 瘦身版）

> 目标读者：写代码的人。看完这份文档应当能直接动手，不需要再问「为什么」。
> 前置文档：`docs/技术设计-诊断内核与API医生.md`（1.1 期诊断内核）、`docs/产品规格-PRD-1.x.md`。
> 本文所有数字都是 2026-11-14 00:29–00:56 在真实安装目录 `E:/VPNTray-2.5.7`（版本 1.0.1）上实测的，不是估算。

---

## 0. 一句话结论

**我们自己的代码只有约 1.8 万行、资源 1MB，但用户装到手的是 343MB、常驻 160MB、每秒烧 4% 单核。**

343MB 里 318MB 不是我们写的：mihomo 61MB、地理数据 29MB、numpy 28MB、PIL 13MB、cryptography 10MB、日志 8MB。
每秒一次的 `/api/state` 轮询要 100ms，其中 **101ms 花在一个叫 `ocrbridge.status()` 的函数上**——它每次都跑 `netstat -ano` 和 `tasklist`，只为在界面上显示一个「已就绪」。

所以这份文档不谈架构大改，只做三件事：**把不是我们的东西剔出去、把每次轮询都干的活变成按需和缓存、把该异步的写盘挪走。** 做完预计：安装体积 343MB → 165MB，`/api/state` 100ms → 12ms，常驻 CPU 4% → 0.6%。

### 1.4 三个根因（已定位到行）

**根因 A：`/api/state` 里的 `ocrbridge.status()` 每次跑两个子进程。**

`vpntray/webui.py` 的 `_ocr_state(app)` → `vpntray/ocrbridge.py::status()`：
- `_pid_on_port(port)` 跑 `netstat -ano -p TCP` 再逐行解析 → 约 20ms
- `_image_of(pid)` 跑 `tasklist /FI "PID eq n" /FO CSV /NH` → 约 60ms
- `health(port)` 打一次 `/health` → 1.2ms

实测直接调用 `ocrbridge.status()`：**101ms**（`/health` 只占 1.2ms）。而 `/api/state` 的总耗时就是 100ms——也就是说**整个状态接口的时间几乎全被这一个函数吃掉了**，前端每 1.8 秒付一次。

**根因 B：`Settings.save()` 是同步的 DPAPI + fsync。**

`vpntray/settings.py::save()` 每次调用：`CryptProtectData`（封 secret / ai_api_token / campus_pass）+ `json.dumps` + 临时文件 + `os.fsync` + `os.replace`。实测 **119ms**。`POST /api/ai/api` 无论字段有没有变都 `s.save()`，于是每次 90ms+。

（好消息：`/api/state` 轮询期间 `data/settings.json` 的 mtime 不变，说明轮询没有触发写盘。`Settings.load` 实测 0ms。）

**根因 C：`app.topo()` 每次真的去查网络。**

`vpntray/app.py:402 topo()` 里 `geolink.own_ip()`、`geolink.entry(node)`、`geolink.exit_point(...)` 都是实时请求，没有 TTL 缓存、没有短超时。三次采样 8.0s / 3.8s / 0.17s——前两次是冷路径在等 HTTP 超时。

## 3. 体积：把不是我们的东西剔出去

### 3.1 打包排除（一次性收益 38MB，改动 3 行）

`release.ps1` 第 33–41 行的 PyInstaller 参数里加：

```
--exclude-module numpy --exclude-module pandas --exclude-module scipy
--exclude-module matplotlib --exclude-module cryptography --exclude-module OpenSSL
--exclude-module setuptools --exclude-module pip --exclude-module pkg_resources
--exclude-module tkinter --exclude-module unittest --exclude-module pydoc_data
```

依据（不是猜的）：
- `numpy` / `cryptography` 在 `vpntray/**/*.py` 里 grep 零命中；
- `build/VPNTray/xref-VPNTray.html` 显示 `cryptography` 的引用来源是 `OpenSSL.SSL`、`OpenSSL.crypto`——即本机装了 pyOpenSSL，被 `urllib3.contrib.pyopenssl` 的可选路径整包收进来了；我们发 HTTPS 请求走 `ssl` 模块，不需要它；
- `numpy` 是 PyInstaller 的 hook 在检测到包存在时整体收进（连带 `numpy.libs` 里的 OpenBLAS 21MB），没有任何一方真正 import。

**验收方式（必须做，别只看体积）**：出包后跑 `build/smoke_live.py` 全 12 项 + 手工点一次「测速」「纯净度」「检查更新」——这三条分别覆盖 requests/ssl、JSON 解析、DPAPI 写盘。

### 3.2 PIL 保留但裁件（-6MB）

托盘图标只用 `PIL._imaging`（`pystray._win32` 需要 `Image`）。可以额外排除 `_imagingtk`、`_imagingcms`、`_avif`、`_webp`、`_imagingmath`（各几百 KB 到 2MB）。做法是在打包后处理阶段删 `_internal/PIL/*.pyd` 白名单之外的文件，**不要**用 `--exclude-module PIL`（会连 `_imaging` 一起没了，托盘图标直接崩）。

### 3.3 地理数据：从「随包带」改成「按需取」（-29MB）

现在 `data/` 里 GeoIP.dat 16MB + country.mmdb 8MB + GeoSite.dat 5MB 是随包发的，安装目录直接 +29MB。而这一堆只在**内核首次启动**时需要。

方案（按收益/风险排序，选 B）：
- **A 换精简数据**：用 `geosite.dat` 只保留 CN 分类，GeoIP 用 `geoip-only-cn-private.dat`。体积 29MB → 6MB，但订阅里出现其他国家规则时会走 GEOIP 兜底，行为不变但「更粗」。风险低，收益中。
- **B 首次运行下载**（推荐）：包里不带，`kernel.ensure_geo_assets()` 已存在（当前按 SHA256 + sidecar 比对），改成「缺失则下载」。下载源用 GitHub release 或 我们的 release 资产，带 SHA256 校验（复用 `updater._resolve_zip_sha` 的思路）。首启多 3–8 秒（有进度条），换来安装目录 -29MB，且升级包不再重复下这 29MB。
- **C 引导器按需解压**：把地理数据打进 zip，首次运行解压。收益同 B 但实现更绕，不选。

注意：方案 B 要处理「下载失败」——**必须**退回内置最小 GeoIP（否则内核起不来），并在 `/api/state` 的 `kernel_skip` 里给出原因。

### 3.4 日志滚动（-8MB 且不再无限涨）

`data/logs` 已 8MB 且只增不减。`vpntray/logger.py` 换成 `logging.handlers.RotatingFileHandler(maxBytes=2MB, backupCount=3)`（app.log / kernel.log 各自一份），总量封顶 6MB。顺手在「打开日志目录」旁边加一个「清理旧日志」按钮。

### 3.5 清掉包里的垃圾（-1.5MB）

`_internal/` 里现在有 `*.dist-info/`、`__pycache__`、`.pyi` 中间产物。release.ps1 收尾加一步：删 `_internal/**/*.dist-info`、`_internal/**/__pycache__`，保留 `*.pyd`/`*.dll`。

### 3.6 mihomo 61MB 怎么办

**不动。** 它是内核，替代品（sing-box 等）体积相近而稳定性未知。真要减，只有「首次运行下载内核」一条路，但内核启动失败 = 整个软件不可用，风险远大于 61MB 的收益。文档写下这条是**为了制止以后有人再提一次**。

## 4. 性能：把每次轮询都干的活变成按需

原则：**轮询路径上禁止出现子进程、网络、磁盘同步写。** 这三类操作只允许出现在「用户点了按钮」或「后台线程」里。

### 4.1 P0：`/api/state` 去子进程（100ms → 12ms）

`ocrbridge.status()` 的问题是它每次都在回答「OCR 桥还活着吗」这个**不需要毫秒级新鲜度**的问题。

改法（两层，先做第一层就够）：

1. **TTL 缓存**（改动最小，20 行）：`vpntray/ocrbridge.py` 加模块级 `_CACHE = {"at": 0.0, "val": {}}`，`status(max_age=5.0)`：`time.monotonic() - _CACHE["at"] < max_age` 直接返回深拷贝。所有写操作（`start/stop/restart`）在成功后 `_CACHE["at"] = 0` 失效。
2. **换掉子进程**（第二阶段，收益 20ms → 0.3ms）：新增 `vpntray/procwin.py`，用 ctypes 直接问 Windows：
   - 端口 → PID：`iphlpapi.GetExtendedTcpTable`（`TCP_TABLE_OWNER_PID_LISTENER`），一次返回全部监听，解析约 0.2ms；
   - PID → 进程名：`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW`，约 0.1ms；
   - 保留 `netstat`/`tasklist` 作为非 Windows 或 API 失败时的兜底（现在这段代码原样留着）。

**DoD**：`curl -w %{time_total} /api/state` 连续 10 次，p95 ≤ 15ms；`tests/test_ocrbridge.py` 里 mock `_pid_on_port` 断言缓存命中时不再被调用。

### 4.2 P0：`/api/state` 从 37KB 拆成 core + 段落（-70% 字节）

现在 `build_state()` 一次性吐全部：`proxies`、`nodes`、`modules`、`netdoc`（13 项体检全文）、`trade`、`campus`、`ocr`、`ai_api`……前端一秒多就要收 37KB 并全量重渲染。

改法：
- `GET /api/state` 只回 **core**：`ui/phase/kernel_ok/mode/group_now/group_all/ports/progress/sysproxy/dns/update/ai_api(掩码)/counts`，目标 ≤10KB；
- 其余按需：`GET /api/state?part=nodes|modules|netdoc|trade|campus|ocr|subs`（`part` 用 `{a,b}` 白名单校验），前端**只在对应页面可见时**拉一次，并在页面切换时拉；
- 加**版本号短路**：`build_state` 末尾算 `ver = state["ver"]`（已有 `_changed()` 计数，直接暴露），handler 支持 `If-None-Match: "<ver>"`，命中返回 `304` 空体——空闲时（无进度、无任务）前端轮询成本≈0.3ms。

改动点：`vpntray/webui.py::build_state`（拆函数，不动内部逻辑）、`assets/index.html` 的 `render()`（把各 `renderXxx` 改成读 `S.parts` 缓存）、`api()`（默认带 ETag）。

**DoD**：空闲 60 秒内 `/api/state` 平均响应 ≤2ms（全 304）；切到「扩展」页后 1 秒内 `netdoc/ocr/campus` 段落到位。

### 4.3 P0：`Settings.save()` 异步化（119ms → 2ms）

现在每次开关都同步做 DPAPI + fsync + replace。用户体感是「点开关卡一下」，实测 119ms。

改法：
- `save()` 拆成 `save_sync()`（保留旧语义，退出/升级前调用）与 `save()`（**脏标记 + 合并写**）：`self._dirty = True; self._schedule()`，后台线程 `threading.Timer(0.8)` 合并 800ms 内的所有改动，写一次；
- **去掉 settings 的 `os.fsync`**：settings.json 丢了最多是「上次改的开关没记住」，不值得每次付 40ms。`data/modules/*.json` 的 fsync 保留（模块是用户手写的配置，值得）；
- DPAPI 只封 3 个凭据字段（已经是这样），把 `CryptProtectData` 结果按 `(key, 明文 sha1)` 做内存缓存，值没变就不重新加密；
- `POST /api/ai/api` 只在字段真变了才 `save()`（现在无条件）。

**DoD**：`tests/test_settings_secure.py` 加 `test_save_is_debounced`（连改 10 个键只落盘 1 次）与 `test_save_sync_writes_immediately`；`POST /api/ai/api` 往返 ≤10ms。

### 4.4 P1：`topo()` 加缓存与短超时（8s → 20ms）

`app.topo()` 依赖 `geolink.own_ip/entry/exit_point`，三次采样 8.0/3.8/0.17s。

改法：
- `geolink` 每个函数加 `_TTL` 缓存（`own_ip` 600s、`entry` 3600s、`exit_point` 300s），键是节点名/IP；
- 所有外部请求超时压到 **1.5s**，失败返回 `None` 而不是抛（拓扑本来就允许「不知道」）；
- `topo()` 只读缓存，缓存缺失时返回 `ready=False` 并起后台线程去补——前端先画出「节点 → 入口」，落地出口晚 2 秒补上；
- 启动后 5 秒预热一次（跟 `test_delays` 的调度合并，不额外起线程）。

**DoD**：`POST /api/topo` 冷启动第一次 ≤1.6s，之后 ≤20ms；断网时 ≤1.6s 且 `ready=false` 不抛错。

### 4.5 P1：前端轮询节流（4% → 0.6% 单核）

`assets/index.html` 现在：`pollWait()` 在有 `progress` 时 700ms、否则 `POLL_FAST=1800`，页面隐藏时已在退避。

再收三刀：
1. **空闲降频**：连续 3 次响应 `304` 或状态无变化 → 2.4s → 5s（上限 10s）；有任务/有 progress 时回到 700ms；
2. **只在需要的页面拉重段落**：概览页只拉 core，节点页才拉 nodes；
3. **停止无意义重渲染**：`render()` 开头比较 `S.ver`，没变就只跑 `renderProgs`/`renderTop`（这两个便宜），跳过 `renderNodes`（28 行 DOM 重建）。

**DoD**：`build/metrics.ps1` 观察 3 分钟，CPU 时间增量 ≤1.8s（约 0.6% 单核），且界面在切节点/开任务时仍是秒级响应。

### 4.6 P2：写盘与网络一律进后台

盘点现有的同步网络调用，全部改成「后台线程 + 状态字段」：`update_check`（已异步）、`sub.refresh`、`purity`（已后台）、`speed`（已后台）、`campus.login`（按钮路径允许同步，但要有 6s 超时 + busy 态）。规则一句话：**HTTP handler 里不允许出现超过 50ms 的阻塞调用**，超了就挪后台，前端看 `progress`。

## 5. 内存：60MB 里有什么

| 组成 | 估算 | 处置 |
|---|---|---|
| Python 3.12 解释器 + stdlib | 18MB | 不动 |
| pywebview / WebView2 桥 + CLR | 12MB | 不动（界面就靠它） |
| PIL 图像对象（图标，多尺寸） | 6MB | 图标改为**首次用到时**再 `Image.open`，并在 5 分钟后 `close()`（现在疑似常驻） |
| requests / urllib3 / ssl 会话池 | 5MB | 复用 `Session`，别每次 `requests.get`（`geolink`/`purity` 已在部分地方新建） |
| 状态字典（proxies/connections 缓存） | 8MB | `connections` 只保留最近 200 条（诊断内核采集层同样约束） |
| 其它（模块/订阅/UI 数据） | 11MB | 不动 |

目标 45MB 靠三条：PIL 懒加载、Session 复用、connections 截断。**不要**为了省内存去换 UI 框架（pywebview → Qt 会涨 40MB）。

## 6. 度量与门禁（没有度量就没有优化）

### 6.1 三个脚本（都进仓库，`build/` 下已有雏形）

| 脚本 | 作用 | 输出 |
|---|---|---|
| `build/metrics.ps1` | 工作集/私有/线程/句柄/CPU 时间，采样 N 次 | 表格 + JSON |
| `tools/bench_state.py` | 连打 `/api/state` 30 次 + 拆分段落，输出 p50/p95/max 与响应字节 | 表格，非 0 退出码表示超预算 |
| `tools/disk_budget.py` | 递归统计安装目录，按 §2 预算逐项比对 | 超预算 → exit 1 |

两个脚本已落盘并在 1.0.1 上实跑过，当前输出（即基线，也是下一次要打败的数字）：

```
GET /api/state  n=20  p50=127.1ms  p95=139.2ms  max=139.2ms  body=37600B   -> 超预算
.            341.8MB  (预算 165MB)  超
_internal     72.5MB  (预算 80MB)   ok
bin           85.6MB  (预算 90MB)   ok
data          35.2MB  (预算 14MB)   超
_internal 最大几项：numpy.libs 20MB，PIL 13MB，cryptography 9MB，python312.dll 7MB，numpy 6MB
```

### 6.2 接进发布流程

`release.ps1` 收尾追加：
1. `python tools/disk_budget.py release/VPNTray-<ver>` —— 体积超预算直接失败，不产出 zip；
2. 打包后把 `VPNTray-<ver>-win64.zip` 大小写进 `SHA256SUMS.txt` 旁边的 `BUILD-INFO.txt`（体积趋势可追溯）。

`build/deploy.py` 启动后追加：跑 `tools/bench_state.py`，`/api/state` p95 > 15ms 就红字警告（不阻断，但每次都能看见）。

### 6.3 不许加的新依赖

以下任一出现即视为破坏本设计（评审时直接打回）：`numpy`、`pandas`、`scipy`、`matplotlib`、`cryptography`（直接用 `ctypes` 调 DPAPI 已有实现）、`PyQt/PySide`、`aiohttp`（`requests` 够用）、任何「顺手引入的 ORM」。需要新依赖时，先在 PR 描述里写清「体积 +XMB / 内存 +YMB」，再决定。

## 7. 实施顺序（每一步都能独立发布）

## 8. 风险与反悔点

| 风险 | 影响 | 缓解 |
|---|---|---|
| `--exclude-module` 排掉了某个隐形依赖（例如某次 requests 版本启用 pyopenssl） | 运行时 ImportError，用户端全断 | smoke_live + 手工点测速/纯净度/更新；排错时先看 `_internal` 里少了谁 |
| `Settings.save` 异步导致退出时丢最后一次改动 | 用户改了开关，下次打开还是旧的 | 退出/重启内核/升级前强制 `save_sync()`；`atexit` 兜底 |
| 拆 `/api/state` 让第三方脚本（AI 客户端、用户自己的 curl）失效 | 兼容性投诉 | 保留 `?part=all` 返回旧结构；`aiops status` 工具继续读内部完整状态，不走 HTTP |
| 地理数据按需下载失败 | 内核起不来 | 包内保留**最小** GeoIP（仅 CN 段，约 1MB）；下载失败时用它启动并提示「规则精度下降」 |
| 缓存让「点了开关但界面没变」 | 用户困惑 | 所有写操作后主动失效缓存；TTL 只用于**只读状态**，不用于配置 |

**反悔点（明确写下不做）**：不换 UI 框架、不动 mihomo、不引入异步框架（asyncio）、不做插件热重载、不把 index.html 拆成构建产物（保持单文件 + 可 `node --check`）。

## 9. 与 1.1 期诊断内核的关系

1.1 期诊断内核（`docs/技术设计-诊断内核与API医生.md`）要在 `app.py` 里加采集线程，本文的 P0/P1 正好是它的前置条件：

- 诊断内核每 2 秒轮询 `/connections`，实测只要 1.8ms，**安全**；但它的报告页要读 `state`，所以 `/api/state` 必须先轻量化，否则诊断功能一开，轮询成本翻倍；
- 诊断内核的 `store`（事件落盘）会写 SQLite/JSONL，必须走后台写线程 + 批量提交，复用本文 §4.6 的「handler 内不阻塞」原则；
- 本文 §6.3 的「不许加的新依赖」同样约束诊断子包（不得为了解析日志引入 `pandas`）。

顺序建议：**先做本文 P0（1.5 天）再开工诊断内核**，否则诊断内核会在一个每秒 100ms 的底座上叠加采样，把 CPU 顶到 10%。
